# 切枪 178 错误定位（2026-10-16）

状态：第三轮已定位首次初始化重复清零的根因，修复已接入；会话 646b9593 日志和用户实机确认通过。下文前两轮保留为调查过程，结论以最新一节为准。

## 已有现场与结论

对照 `.lobby/c53bb373/result.json` 与较新的 `.lobby/18edbac2/result.json`，两次均为：

- 错误文本 `178 0 ** 110 0 32 1341 522 3100 left`，错误码 2。
- 栈顶返回地址 `0x485d42`，EBX=1，EDI=0xf2（武器索引 242）。
- `stopped_reason=Stopped at diagnostic engine error`，`child_terminated=true`。

`session.py` 在引擎错误断点恢复原字节后，对非白名单错误跳出调试循环，随后在
`finally` 调用 `TerminateProcess`。因此两次记录中的直接退出机制是宿主终止。
但这不证明引擎错误可以安全忽略，更不证明放行后可以继续切枪。

## 由当前版本机器码确认的触发条件

以哈希绑定的恢复镜像反汇编，并核对 18edbac2 实际运行副本：
`0x40bfe0..0x40c02f`、`0x4824a0..0x482bdb`、`0x485b20..0x485ded`
三个代码区间与恢复镜像逐字节一致。

1. `0x485b20` 的武器更新函数读取当前武器；`0x485c0e..0x485c7d`
   综合装备槽记录第 2 字节和武器定义 `+0xc0d`，决定是否需要处理左手。
2. 每只手有 0x18 字节对象记录。`0x485d0a` 检查记录首指针是否为零。
3. 非零时进入正常更新；零时在 `0x485d13..0x485d3d` 构造 178 错误。
   EBX=0 对应 right，EBX=1 对应 left；武器内部名来自定义的首指针。
4. 两次现场 EBX=1、返回地址=0x485d42，故可确认：**需要处理的左手第一人称
   武器对象为空，原生客户端主动报告错误，随后宿主结束整个客户端。**

格式串中 `%d` 为本地客户端编号 0；第一个 `%s` 为 `** 110 0 32 1341 522 3100`，
第二个 `%s` 为 left。不能把 0 当成缺失资源编号，或把这条消息解释成 USP 文件缺失。

另一个取证细节：该调用点先在 `0x63cb50` 格式化字符串，再把成品文本传给
`Com_Error`。旧结果的 `error_arguments` 是余下的栈槽，其中包含格式化调用残留参数，
不能统一当作 `Com_Error` 的正式变参解释。

## 尚待区分的上游原因

创建路径 `0x4824a0` 也检查双持状态，按手别创建对象并写回记录。
现有日志没有保存装备槽、创建时状态、左右手对象或动画树，无法判定：

- 装备/双持状态错误或创建、更新两处观察到的状态不一致；
- 左手对象创建失败或创建后被清除。

不能直接将 C1 版本的 playerState/WeaponDef 偏移套用到 2.6.9.7；本次偏移均取自
本机哈希绑定的 2.6.9.7 恢复镜像。也没有证据把问题归咎于服务端的某个字段。

## 第三轮：创建过程与根因（会话 96f091a6）

`weapon-build-trace.jsonl` 记录了主武器 241 的完整创建与双持武器 242 的失败。
双持武器进入 `0x4824d7` 时两个模型参数均为 0，随后直接到达 `0x482bd7` 返回，
完全没有进入每手检查或对象分配。此前仍非零的右手对象来自上一把武器，不能将其
解释成 M9 右手创建成功。这里的首模型参数准确说是第一人称手臂/基础模型，
对应 WeaponDef+0x10；它与前文检查的 +0x14/+0x18 枪械模型不是同一字段。

对当前恢复镜像 `0x482110` 的反汇编确认：

1. 冷缓存的 `+0x14` 就绪字段为零，`0x48215e` 首次 memset 清空 0x124 字节。
2. `0x482182..0x482185` 从 WeaponDef+0x10 读取模型并写入缓存首字段。
3. 就绪字段仍为零，`0x482199` 再次 memset 清空整个缓存，把刚写入的模型抹掉。
4. 函数设置就绪字段并返回。`0x485cdc` 从缓存取出零模型传给创建函数；
   创建函数在 `0x4824ff..0x482502` 因模型参数为空提前返回。
5. 单持场景可能暂时沿用上一把武器右手对象，并在下次更新填回模型；
   第一次需要双持时没有旧左手对象可沿用，因此立即命中 `178 ... left`。
   这解释了用户 USP 可用而 M9 双持失败的对照，不意味着所有单持组合均已验证。

旧项目 `D:/Games/Launcher source code/server2697/weapon_view_cache2697.py` 有同一修复，
其 SHA-256 为 `f13049973ed1ebe5f68e974f4d4694eeb19d6d2f21bddd7ba7d2bfe1291f6cd3`。
当前新项目原先没有该修复。参考文件无单独许可证声明，保留现有来源边界；
新模块独立实现，不在运行时导入旧项目。

修复位于 `v2697/weapon_cache.py`，由 `patches.py` 每次构建副本时应用：
只将 `0x482199` 的 5 字节 call 替换为 NOP，调用者原有栈清理仍执行。
首次清零、模型赋值、就绪标志、原生左右手创建及 178 错误检查全部保留。
整镜像 SHA-256 校验之外，还核对三处初始化指令，失败时不写补丁。
补丁登记在会话的 `preview-patches.json` 中。

验证：客户端 40 项测试通过，新增补丁范围及错误版本拒绝测试；相关文件编译检查通过。
创建跟踪由环境变量 `CODOL_TRACE_WEAPON_BUILD=1` 显式启用，每点最多 256 次，
正常启动默认关闭。修复后实机回归会话为 `646b9593`：双持首次创建的基础模型参数为
`0x1e34c5c`（不再为零），右手对象返回 `0x2c629b8`，左手对象返回 `0x2c62a84`；
后续重建也两手成功。最终 `stopped_reason=null`，仅有正常 `EXE_DISCONNECTED`，
无 178 错误。用户对首次切枪、来回切换、双枪显示及开火验证请求明确回复“修好了”。
本结论覆盖本机 M9 双持此次实机路径，不代替所有武器组合或长时间稳定性验收。
