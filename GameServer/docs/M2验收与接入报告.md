## 1. 当前能做什么

- 控制服务独立启动；客户端通过 `StartOnline.cmd` 建立真实 HTTP 玩家通道。
- 在游戏原生大厅点击创建房间，服务端保存同一个房间；返回完整成员、地图、模式、阵营与 Bot 配置。
- 原生房间切换阵营、房主切换地图，通过服务端校验并增加版本，再投影回原生 UI。退出房间同步关闭当前单人房间。
- 修复房间背景、角色预览/相机、自己身份识别和装备显示。用户在最终修复后反馈“修好了”；不据此声称所有装备组合均已验收。
- 管理页具备真实房间列表和 Bot 数量、阵营、难度配置；服务端具备权限、容量、幂等、版本冲突和持久事件处理。
- 当前可配置 25 张安装地图、`war` 模式。这只是房间配置目录；M0 真实空地图运行仍只证明 `mp_cross_fire/war`。

## 3. 这次为什么出现“按钮能点，界面不变”

服务端分配的玩家 ID 是 `6363899815`。原生 AS_GetPlayerID 的一个调用点采用特殊寄存器顺序，
桥接曾按通常的 64 位返回方式写入，客户端实际认成 `8885997506735898625`。
房间成员与“自己”不再对应，影响自己的阵营显示、房主地图权限以及装备绑定。
旧测试 ID `4294967297` 的高低 32 位都是 1，掩盖了顺序错误。

已在 `Client/src/codol/v2697/staging.py` 的 `install_identity` 修正：
`0x5b9717` 所在调用点 EDX=低 32 位、EAX=高 32 位，后续原生指令先 push EAX 再 push EDX。
另一个原生 getter `0x749620` 仍采用通常的 EAX 低位、EDX 高位，不能一并反转。
回归校验工具使用高低不同的 ID，防止同类问题再次被测试种子掩盖。

原生名单确有 UI 缓存，但本次核心原因是身份不一致；强制刷新不能修正身份。
背景问题另由原生预览场景、角色外观及相机初始化修复。
此前还修复了：原生创建时携带运营期随机默认地图导致拒绝、错误码误显示“人数超过上限”、
邮箱日志参数同名导致工作线程退出，以及旧 SSE 快照覆盖较新命令结果。
未保留缺乏证据的武器查询拦截补丁。

## 4. 实际模块与状态所有权

```text
原生 UI 意图 → 版本 DLL/固定邮箱 → Python 玩家通道 → HTTP 命令
                                                    ↓
                  管理 UI → 管理 API → 应用用例 → 领域校验 → SQLite
                                                    ↓
原生安全队列 ← 版本投影/固定邮箱 ← Python 玩家通道 ← SSE 完整快照
```

| 模块 | 职责与边界 |
| --- | --- |
| `control/src/codol_control/domain/room_rules.py` | 房间配置、容量与版本规则，不含原生地址和框架 |
| `application/player_rooms.py`、`ports.py` | 身份/会话/房间用例及依赖接口，服务端拥有权威状态 |
| `infrastructure/online_repository.py`、`migrations/0002_player_rooms.sql` | SQLite 事务；房间快照、幂等回执、事件同事务提交 |
| `transport/player_routes.py` | 玩家/管理员权限分别校验，HTTP 意图与 SSE 推送 |
| `Client/src/codol/online/channel.py` | 开发身份、HTTP、SSE 和重连，不含版本地址 |
| `v2697/room_mailbox.py` | 后台线程消费意图并发布投影；nonce、序号与原子替换隔离运行会话 |
| `v2697/room_staging.py` | 验证原始字节、安装版本补丁、原生安全队列入口 |
| `Client/native/room_bridge2697.cpp` | 原生房间适配、有限意图、成员投影；不访问网络、不启动战斗 |
| `room_preview2697.h`、`room_flash2697.h` | 角色/相机预览与 Flash 绑定细节，与业务规则分开 |

网络线程不直接调用 UI；原生回调由客户端自己的安全队列消费。
协议与邮箱有界；意图携带幂等键与期望版本；SSE 并发到达的旧状态不能回滚新确认。
ADR 0004 记录 HTTP+SSE 的选择、开发身份边界和版本适配约束。
原生地址、布局和部分算法依据旧研究移植整理，生产运行不依赖旧项目，不能宣称全部从零重写。

M1 接手核对还修复了重复启动实例在端口绑定失败前覆盖 control.json 的问题：
当前先绑定端口再发布控制文件，真实第二进程回归通过；应用服务依赖改经 ports 注入，
诊断文件读取、凭据写入和房间查询等细节收敛到基础设施实现。

## 6. 启动和复核入口

先启动 `GameServer/control/Start.cmd`，再启动 `Client/StartOnline.cmd`；
原有 `Client/Start.cmd` 保持离线大厅。退出客户端用 `Client/Stop.cmd`，停控制服务用其自己的 `Stop.cmd`。

在工作区根执行：

```powershell
.\Client\python\python.exe -X utf8 -m unittest discover -s Client/tests -v
.\GameServer\python\python.exe -X utf8 -m unittest discover -s GameServer/control/tests -v
.\Client\python\python.exe -X utf8 Client/tools/build_room_bridge.py
.\Client\python\python.exe -X utf8 Client/tools/verify_room_bridge.py
```

最后两项分别为桥接构建和副本/PE/身份顺序验证，不替代 GUI 验收；不因文档更新自动启动游戏。
`verify_m2_projection.py` 会启动真实客户端并停止/重启控制服务，运行前核对独占会话及权限。

## 8. 结构验收结论与交付范围

M2 符合 ADR 0002 的本期边界：服务端领域/应用拥有房间权威，原生地址和布局只在版本适配；
Python网络线程持有HTTP/SSE与邮箱写入，原生安全队列持有Flash与预览调用；DLL无网络导入。
清除了无人引用的M1空仓库，实际依赖扫描纳入回归。新增/修改代码有中文职责及函数说明。

这不表示全引擎重构或第三方中文说明已经完成。后续实际模块、方法和关口仍按 §5 与R0报告 §3：
M3先整理 `native/tools/` 构建引用、筛选 `native/tests/` 协议基线，再建立生产战斗生命周期；
M4处理Bot/导航与相关game依赖；M5处理发行构建、来源/许可证与维护说明；M6验证身份和实例隔离。
当前未启动战斗、未生成Bot实体，未验证多人或公网；25张可配置地图不等于25张可战斗地图。
