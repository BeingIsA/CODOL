# M3 验收与接入报告：客户端入场与独立战斗连接

日期：2026-10-16。状态：**功能与结构验收已完成（本机单客户端边界）**。
前置 M0、R0、M1、M2 已完成。不能把本报告理解为 Bot 对战、真实战斗规则或多人联机已经完成。

## 1. 当前能做什么

- 在真实原生大厅点击「创建房间」，服务端保存同一个房间；进入房间后点击原生
  **「开始游戏」**，控制服务启动**独立原生战斗进程**（不是同进程、不是空地图占位），
  客户端**从原生房间真实入场进入地图**。
- 入场后玩家可出生、移动、转视角、开火、换弹——由用户在真实 GUI 会话中人工核对通过。
- 管理员或房主停止对局后，客户端**明确断开**并**回到房间界面**，房间恢复 `OPEN`，
  可以**再次开局**（第二局已实测）。
- 玩家在对局中点原生「返回大厅」，服务端受理离开：**移除本人席位**，房间无人即关闭
  （2026-10-16 实测，见 ADR 0006）。
- 管理页具备房间卡片「开局/停止对局」按钮与运行时页对局面板（活动 + 最近）。

当前战斗地图仍只有 `mp_cross_fire / war` 是**已验证可入场**的组合；25 张可配置地图
不等于 25 张可战斗地图。Bot 名额仍是房间占位，不是真实实体（M4）。

## 2. 为什么需要这些改动，数据怎样流动

M2 结束时客户端只连到房间，**没有连到任何战斗进程**。M3 要接的是"第三个通道"：
原生引擎自己的 UDP 战斗连接。三条通道职责分离是本期最关键的设计边界：

```text
控制通道（M2 已有）  管理 UI / 玩家宿主  ←HTTP+SSE→  控制服务（房间与对局唯一权威）
监督通道（本期新增） 控制服务           ←RCON/UDP→   原生战斗进程（native-runtime-v1 契约）
战斗通道（本期新增） 客户端原生引擎      ←原生 UDP→   原生战斗进程（28969，Python 全程不触碰）
```

入场的数据流：

```text
原生「开始游戏」按钮 → DLL 发 kind 5 意图 → 玩家通道 POST /player/match-start
   → 应用用例（房主校验）→ 领域校验 → SQLite 落对局
   → 控制服务按契约启动原生战斗进程 → LOADING→READY（≥4 采样、时钟严格递增、≥4000ms）
   → 房间快照携带入场信息（host/port/map/gametype）
   → SSE 下发 → 客户端 room_mailbox 写 m3-match.bin 对局投影
   → DLL 消费投影：调原生连接初始化 → 引擎按标准 challenge/connect 进入地图
   → 服务端观察到 CS_PRIMED→CS_ACTIVE、humans=1、active_uids 命中成员 native_id
```

停止时不再"硬杀"：控制服务先发 RCON `sh1x_endmatch`，向已入场的真人客户端投递原生
离场命令 → 客户端原生走良性离场路径（state 归零）→ DLL 帧钩子关套接字并回房 →
服务端确认入场人数归零后才 `quit`。

### 4.1 本期修复的三个真实缺陷

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 停止对局后客户端不回房，干等 UDP 超时，引擎弹 `EXE_ERR_SERVER_TIMEOUT` | 服务端停止路径只有 RCON `quit` **硬杀**，客户端收不到任何告别信息 | 契约 revision 3 新增 `sh1x_endmatch`；`supervisor.stop` 改为 endmatch → 等入场人数归零 → quit |
| 客户端收到 `EXE_MATCHENDED` 后**宿主把良性通知误判成引擎错误**并终止会话 | `is_battle_disconnect` 白名单只认 `EXE_DISCONNECTED/EXE_SERVER_DISCONNECTED/EXE_SERVERQUIT` | 白名单纳入 `EXE_MATCHENDED`；`EXE_ERR_SERVER_TIMEOUT` 等仍严格失败 |
| 原生「返回大厅」后客户端回到大厅主界面，**服务端房间悬空 OPEN** | 房间规则按单人写："离开=关闭房间"，且对局中拒绝离开；房间关闭后对局收尾还会把它"复活"成空房间 | 语义改为"离开=移除席位、空房即关闭、对局中允许离开"，并对局收尾不再复活已关闭房间（**ADR 0006**） |

三项均配了回归测试（控制服务 2 项 + 房间生命周期 11 项、客户端 1 项），全部先失败后通过。

**MinGW 编译移植的四个坑（已解决，后续改动原生链接代码时会再遇到）**

1. MSVC `__asm {}` 块与 `__declspec(naked)` 组合 MinGW 不支持 → 改 GCC
   `__attribute__((naked))` + `asm volatile()` 字符串（与既有 `status_tick` 同模式）。
2. 内联汇编改 AT&T 语法：`pushfd/pushad/popad/popfd` → `pushfl/pushal/popal/popfl`。
3. C++ static 函数被名字改编（`__ZL13m3_local_send…`），内联汇编里 `$_m3_local_send`
   解析不到 → 三个回调改 `extern "C"` + `used` 属性。
4. 32 位 PE 的 C 符号带下划线前缀；`-lws2_32` 必须放在源文件之后（GNU ld 顺序敏感）。
   链接期报 `undefined reference` 时先用 `-S` 看真实符号名。

**无 GUI 管线验证阶段的三轮修复（每轮都有回归测试钉住）**

| 轮次 | 现象 | 根因 | 修复 |

### 11.6 `178` 号错误的定位进展（2026-10-16 18:20）

**它是什么（已确证）**

`178 %d %s %s` 可在恢复镜像 `0x8b57b4`（原始 EXE `0x49d1b4`）直接检索到，
属于引擎内置的**按数字索引的错误消息表**（同区可见 `169 %s`、`170 %s`、`174 %s`、
`176 %i`、`177`、`179`、`180`、`181 %s %d %d`）。它紧邻的字符串区间**全是武器射击模式常量**：

```
FULL_AUTO_NAME / SEMIAUTO_PUMP_NAME / SEMIAUTO_LEVER_NAME / SEMIAUTO_RIFLE_NAME
DOUBLE_BARREL_NAME / BURST_2_NAME / BURST_3_NAME / BURST_4_NAME / MINIGUN_NAME
csg12 / spas12 / model1887 / ET_NAME
169 %s → void → 170 %s → 174 %s → 176 %i → 177 → right → left
178 %d %s %s   ← 本次触发的这条
```

**即 `178` 是一条武器系统相关的引擎错误消息**，与"切枪时触发"在语义上完全吻合。

**参数已解析（已确证）**

实测消息 `178 0 ** 110 0 32 1341 522 3100 left`，按格式串 `%d %s %s` 拆：

| 位置 | 值 | 说明 |
| --- | --- | --- |
| `%d` | `0` | — |
| `%s` 其一 | `** 110 0 32 1341 522 3100` | 堆上字符串（`0x18A7D3C`），含义未定，疑似武器/配件 ID 序列 |
| `%s` 其二 | **`left`** | 指针 `0xCB69AC` = `0xCB69B4 - 8`，**正好是消息表内 `left` 字符串的位置**，`right`/`left` 就在 `178` 前一行 |

`0xCB69B4` 亦与 PE 节表算出的运行时 VA 一致（原始 EXE 末个 `.tp3` 节），可交叉验证解析无误。

**关键对照：同一通道也承载完全良性的错误**

| 会话 | `0xddab8ac` 命中时的消息 | `error_code` | `stopped_reason` |
| --- | --- | --- | --- |
| `996e1015` | `EXE_MATCHENDED`（服务端对局结束的良性离场通知） | — | **`None`（未停止，会话正常继续）** |
| `c53bb373` | `178 0 ** 110 0 32 1341 522 3100 left` | `2` | `Stopped at diagnostic engine error` |

**即 `Com_Error` 通道承载的错误并非都致命**，是否停止完全取决于 `is_battle_disconnect`
白名单是否放行。上一轮会话在同一地址命中 `EXE_MATCHENDED` 时就没有停。

**仍未确证的两点（不要当成结论）**

1. `178` 在游戏语义上究竟"说什么"——数字索引对应的中文本地化文本尚未找到
   （`Original Client/localization.txt` 内无 `%d %s %s` 条目，该文件的 178 行
   `WIN_ZONE_ERROR` 只是行号巧合）。
2. `error_code = 2` 在本版本 `errorParm_t` 中的确切级别。按 IW 引擎常见枚举
   （`ERR_FATAL=0`、`ERR_DROP=1`、`ERR_SERVERDISCONNECT=2`、`ERR_DISCONNECT=3`），
   `2` **不是** `ERR_FATAL`；若成立，引擎本意是降级/断开而非崩溃退出。
   但**该枚举顺序未在本机二进制中证实**，不能据此下结论。

**一个间接但很强的旁证**：本次 `stopped_reason` 是 `Stopped at diagnostic engine error`
而非 `Captured error dialog before display`——说明引擎**还没走到弹错误框**就被我们在
`Com_Error` 入口拦下并强杀。若真为 `ERR_FATAL`，它后续本应弹窗。
**我们没有证据表明它致命。**

**下一步（唯一能一锤定音的手段）**：改 `session.py` 让此类错误"记录但不停止"，
复现一次切枪。若客户端自行恢复或优雅回菜单 → 坐实宿主误杀；
若随后出现 `0xc0000005` 等真正致命异常 → 才说明引擎确实崩了。
